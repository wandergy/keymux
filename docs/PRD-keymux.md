# Keymux 产品需求文档

版本：0.1 · 2026-11-12 · 产品与设计评审稿

依据：[已确认需求](../AGENTS.md)、[详细技术设计](technical-design.md)。配套：[UI 设计规范](ui/UI-DESIGN.md)、[可点击设计原型](ui/index.html)、[系统图集](diagrams/index.html)。

## 1. 概述

Keymux 是面向团队审批人与自动化系统的多人协同签名应用。首期在 macOS 上，让参与人看懂准确的业务操作、使用本机 Touch ID 授权自己的秘密份额，并按密钥组规则共同产生标准签名。

首期覆盖管理平台业务数据的 Ed25519 签名、Agent 与人工共同签署 Hyperliquid 请求，以及 Solana 交易／消息签名。当前仓库只有需求、技术方案与设计资料；本 PRD 不代表功能已实现。

## 2. 背景

已有两类上游需求：管理平台需要多人批准业务数据；Agent 需要与人工共同授权交易。Solana 等链也需要复用这套协作能力。普通“多人点同意”不能替代多方签名；Agent 获取一次授权后独立下单，也不满足逐次共同签名的要求。

现有操作流程、用户规模与商业模式尚未调研。本稿以已确认的工作任务和安全边界定义首期，不推定已有客户采用了某种钱包或审批产品。

## 3. 目标与成功标准

以下为**首期发布验收目标**，不是已经取得的数据；暂不设商业增长、最大参与人数或签名耗时承诺。

| 目标 | 首期测试环境验收证据 |
| --- | --- |
| 三类任务完整可用 | 业务审批数据可独立验签并防重复执行；Hyperliquid 测试下单可追踪；Solana 测试交易可确认，且分别覆盖人工组与人机组 |
| 授权符合密钥组规则 | 合法参与组合完成签名；不足门限、缺少指定 Agent、重复身份、内容变化及未通过本次本地授权的负例全部阻断 |
| 失败不会误导用户或重复执行 | 中断、取消、有效期变化、提交回执丢失均有明确状态；未知结果不自动重签或发起第二笔操作；生产前完成备份／恢复演练与发行包真机验证 |

可用性评审重点：审核人能辨别“同意”“签名”“提交”“确认”，找到实际操作、网络、账户和参与规则，并能使用键盘完成核对与拒绝。真实用户测试的样本量与通过标准在试点确定。

## 4. 用户与使用场景

| 首期用户群 | 要完成的工作 | 关键约束 |
| --- | --- | --- |
| 业务审批团队 | 对采购、变更等业务审批数据形成可验证的共同授权 | 签的是业务内容；签名不直接代表转账或业务已经执行 |
| 自动化与链上操作团队 | 让 Agent 发起操作，人工核对后共同签名，并跟踪结果 | Hyperliquid 必须人机共签；Solana 按组选择纯人工或人机模式 |

同一团队内有审核人、密钥组管理人和接入方运维等职责。职责划分是设计建议；管理员可以组织成员与配置接入，但不能替代任何人的份额、降低门限或单独恢复密钥。

## 5. 价值主张

| 维度 | 业务审批团队 | 自动化与链上操作团队 |
| --- | --- | --- |
| 谁 | 需要共同负责业务决定的审核人与接入方 | 运行 Agent 的团队、交易审核人与账户管理人 |
| 要完成什么 | 把明确的业务审批内容变成可独立验证的授权 | 让自动化操作保留逐次人工参与和结果可追踪性 |
| 现在如何做 | 未调研；集中签名服务或审批记录仅作为待验证的对比假设 | 未调研；单人钱包、Agent 独立密钥或链上多签仅作为对比方案 |
| 如何帮助 | 展示统一的业务数据，按组门限共同签署并返回标准签名 | 展示真实交易字段，要求指定 Agent 和足够人工共同参与 |
| 完成后的变化 | 上游可以核验内容、签名与操作标识，并防止重复执行 | Agent 无法绕过人工独立签署；签名结果与交易结果分别可查 |
| 替代与选择理由 | 与普通审批记录相比，适用于确实需要标准签名且不希望单方持完整密钥的流程 | 与上述方案相比，适用于需要既有链签名格式、逐次人机共签的场景；不宣称适合所有账户模型 |

Keymux 的价值是把“看清这次操作”和“满足共同签名规则”连成一个可追踪的过程，同时保留各参与方独立控制自己的份额。

## 6. 产品方案

### 6.1 核心体验

首次使用：接受邀请 → 核对工作空间与设备身份 → 检查本机签名能力 → 确认密钥组提案 → 全员协同建钥并持久化 → 激活。

日常使用：进入待办 → 核对来源、用途和实际内容 → 表达同意并等待合法组合就绪 → 针对固定参与集合进行原生确认与 Touch ID → 共同签名 → 验签落盘 → 交付／提交 → 查询目标系统结果。

主界面采用“请求列表 + 审核详情”的工作台。原生确认重复呈现当前请求的关键事实，并绑定本次尝试；此前点过同意不代表本次已经授权读取份额。具体页面、交互与异常状态见 [UI 设计规范](ui/UI-DESIGN.md)。

视觉偏好已确认：支持明暗双主题，默认跟随系统外观。主题变化不改变当前审核内容、授权状态或操作进度。

### 6.2 首期必备能力

| 能力 | 用户可观察的要求 |
| --- | --- |
| 邀请、设备与密钥组 | 区分人工、Agent、设备和客户端；组显示用途、公钥、成员、参与规则、版本与可用状态；未完成全员激活的组不可签名 |
| 两类参与规则 | 纯人工为 t-of-n，2 ≤ t ≤ n；人机为指定 Agent AND k-of-m 人工，1 ≤ k ≤ m；Hyperliquid 不可选纯人工，不允许请求临时降低规则 |
| 三类内容审核 | 业务审批显示业务域、受众、操作标识和审批数据；Hyperliquid 显示环境、账户、订单参数及有效性；Solana 交易显示集群、付款人、指令、账户影响、签名槽及有效高度 |
| 逐次原生授权 | 人工通过本机受保护材料参与；明确本次内容和参与集合；取消或失败不能继续用该次授权；不展示、复制或上传秘密份额 |
| 进度、记录与维护 | 分开记录审批、签名与提交；跟踪未知结果和取消竞态；支持固定成员份额刷新及经验证的分散备份／恢复；危险维护操作显示条件与影响 |

首期签名并不要求全员参与，只要求满足组规则的在线集合；建钥和固定成员份额刷新需要全员参与。同一组同时仅运行一次签名或维护，其他请求显示排队原因。

Solana 链下消息开放时采用独立方法与用途密钥，展示域、原文、受众及有效性，并按固定标准独立验签；未开放的组合明确拒绝，不能回退到交易密钥的任意字节签名。

### 6.3 关键约束与验收情景

| 情景 | 预期体验与结果 |
| --- | --- |
| 参与人离线或缺少必选 Agent | 显示缺少谁及所需规则；满足规则前不长期解锁份额，不用其他人工替代 Agent |
| 内容、参与集合或份额版本改变 | 内容或组版本变化使旧签名包失效，重新准备并创建新请求；仅参与集合变化则结束旧尝试，符合安全重试条件后创建新尝试。两者均重新授权，先核对旧输出 |
| 用户取消、协议中断 | 未产生结果且有证据时才显示已停止；无法排除结果时显示“结果待核对”；发现有效签名则显示“已请求取消，但签名已生成”，阻止自动交付和自动提交，核对是否已对外发送 |
| 链接收但尚未确认 | 显示“已提交，待确认”；按原交易标识查询，不能把回执成功或未查到记录当成最终结果 |
| 交易或请求已过期 | 阻止新签名或不再合法的发送；已签／未知结果仍保留。替换 nonce、blockhash 或操作内容必须创建新请求重新审核 |
| 未知指令、无法解析或来源不可信 | 明确原因并阻止签名，不提供“忽略并继续”盲签入口 |
| 刷新、换机或丢失份额 | 显示冻结与确认进度；刷新不改公钥，改成员或门限需新组及迁移；无合法授权组合时不能承诺恢复 |

### 6.4 技术方向与待定项

已确认采用 cb-mpc，并以 SwiftUI + Flutter + Rust + cb-mpc C API 为技术组合方向。主 UI、原生授权与共享核心的具体职责见技术设计；本 PRD 不新增密码学实现方案。

| 待定项 | 当前设计建议与决定时点 |
| --- | --- |
| Touch ID 与设备覆盖 | 原型按每次授权、不自动回退密码设计；最低 macOS、CPU 和无指纹设备策略需在真机验证阶段确认 |
| 上游格式与链操作范围 | 业务格式与验签合同需对接；Hyperliquid 首先验证下单；Solana 先 legacy/v0 与指令白名单，链下消息按独立用途和方法设计 |
| 拒绝与重试规则 | 原型按一次明确拒绝结束当前请求设计；是否允许其他门限成员继续须单独确认；结果未知始终禁止盲目重签 |
| Agent 与恢复保管 | 部署边界、秘密存储、备份保管与换机授权必须在真实业务前确认；没有默认越权恢复身份 |
| 试点与规模 | 首批试点团队、日请求量、最大 n、延迟目标及可用性目标待调研和基准测试，不能由 UI 示例推定 |

## 7. 发布范围与顺序

按验证结果推进，不给未经估算的交付日期：

1. 验证 macOS 原生授权、共享核心和 cb-mpc 互操作。
2. 打通邀请、两类密钥组、建钥与管理平台业务签名闭环。
3. 依次接通 Hyperliquid Testnet、Solana 测试集群及各自的异常处理。
4. 完成分散恢复演练、份额刷新、发行包验证与安全评估，再评审真实业务开放。

后续扩展其他客户端、链与签名方法；平台移植和方法兼容均需独立验证。首期不提供任意字节盲签、完整私钥导入、链上多签替代、自动降低门限、管理员万能恢复、通用插件市场或 Agent 获一次授权后无限独立签名。

Solana 链下消息是已确认需求的一部分；若第一批试点仅开放交易，必须在支持矩阵和界面中明确标为未开放，不能把“Ed25519 可用”表述为全部消息标准兼容。
