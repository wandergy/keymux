# Keymux UI 设计

版本：0.1 · 2026-11-12 · macOS 首期设计稿

[打开交互原型](index.html) · [产品需求](../PRD-keymux.md) · [技术设计](../technical-design.md) · [架构图集](../diagrams/index.html)

静态预览与受测交互见 [原型检查记录](VERIFICATION.md#页面预览)。

本稿定义信息层级、页面、交互及安全状态。原型中的用户、金额、地址标识和进度均为虚构示例；它不生成密钥、不读取 Keychain、不调用 Touch ID，也不签名或发送交易。

## 1. 设计方向

采用 macOS 审批工作台，默认打开待处理请求。**已确认支持明暗双主题，默认跟随系统外观**；系统切换时同步更新。顶栏“外观”可选择跟随系统、浅色或深色，手动选择优先并在本机保存；存储不可用时仍可在当前页面切换。大面积中性色、克制的蓝色强调和稳定的侧栏让操作内容成为视觉中心；不加入价格走势、资产收益或无来源的“安全评分”。

| 方案 | 优点 | 取舍 |
| --- | --- | --- |
| 请求列表 + 同窗审核详情（本稿） | 比较多个请求时保留上下文，完整展示内容、规则和进度 | 小窗口需折叠列表或改为单列 |
| 单请求分步向导 | 单次操作注意力集中 | 日常处理多个请求时跳转更多；保留给首次配对和建组 |
| 图表型总览 | 容纳运行指标 | 目前没有明确指标需求，不作为默认首页 |

Mac 界面使用宽屏空间和键盘操作，窗口缩小时调整内容布局；侧栏只保留少量顶层目的地。依据 [Apple：Designing for macOS](https://developer.apple.com/design/human-interface-guidelines/designing-for-macos/) 和 [Sidebars](https://developer.apple.com/design/human-interface-guidelines/sidebars)。这些原则不构成最低系统版本或具体视觉材质的兼容承诺。

## 2. 页面结构

| 页面 | 主要任务 | 关键内容与入口 |
| --- | --- | --- |
| 签名请求 | 找到需要自己处理的请求，完成核对 | 搜索／筛选、请求列表、实际内容、来源与环境、密钥组规则、参与人、分阶段进度 |
| 密钥组 | 理解谁能签名，以及当前能否使用 | 用途、公钥、成员角色、活跃设备、组状态、版本、备份状态；创建提案和维护入口 |
| 审计记录 | 还原一次操作发生了什么 | 业务操作、审批、签名、提交的独立事件；请求与尝试标识；错误和恢复证据 |
| 设备与安全 | 了解本机与工作空间连接能力 | 设备绑定、Touch ID 可用性、本地保护状态、支持范围、配对与恢复说明 |
| 原生确认窗口 | 授权当前固定尝试 | 不可编辑的实际内容、当前参与集合、有效性、明确的批准并签名／返回按钮 |

侧栏不放必须参与签名决策的信息；网络、用途、规则和结果状态在详情内再次显示。设计基线为单工作空间，工作空间名称不暗示已支持任意切换。人工人数按独立参与方计数，设备数和界面实例数不计入门限。

### 2.1 请求工作台布局

- 窗口顶栏：当前工作空间、外观选择、测试环境与连接状态；原型另有持续可见的“设计原型／示例数据”标识。
- 左侧导航：固定四个目的地；当前页面用文字、背景和图标共同标识。
- 请求列表：来源与用途、操作摘要、时间、当前状态；选中项始终明确。搜索支持来源、请求编号和操作摘要。
- 主审核区：先显示“要执行什么”，再显示来源、目标、金额／权限、网络和有效性；原始内容与核验字段可展开。
- 协作区与底部操作：完整参与规则、必选 Agent、每人就绪状态，以及“下一步需要谁做什么”；主操作随状态变化，不能始终显示可点击的签名按钮。

设计验收尺寸为 1440×900 与 1280×800。宽度不足时，优先把列表收起为返回入口或让内容单列流动；内容允许垂直滚动，关键字段不得被固定按钮遮挡。页面不通过缩小字体或裁切字段强行压成一屏。

## 3. 内容与视觉规范

| 项目 | 设计规则 |
| --- | --- |
| 字体 | macOS 系统字体；标题约 22–28 px，区块标题 15–18 px，正文 13–15 px；编号与公钥用等宽字。尊重系统放大与文本缩放 |
| 颜色 | 中性背景与表面；蓝色表示选择和主要动作；绿色用于已证实完成；琥珀色表示等待／待核对；红色表示阻断／拒绝。文字和图标始终说明状态 |
| 明暗主题 | 共享语义色变量，分别定义背景、表面、文本、边框与状态色；表单、表格、提示、确认窗口和禁用态一起切换。不用全页面反色，不改变状态含义 |
| 间距 | 4 px 基础步长，主要区域 16–24 px 间隔；表格和字段对齐，长内容自然换行 |
| 按钮 | 同一区域一个主要动作；拒绝和停止使用明确文字。进入原生确认才出现最终签名动作，不把列表选择或 Enter 搜索变成签名 |
| 标识 | 测试环境持续可见；请求编号、组名、来源、公钥可核验。摘要不能取代业务内容；完整标识可展开查看 |
| 数值 | 显示单位、资产、方向和精度；不把 USDC 与 USD 混用。订单价格是订单参数，不展示成实时行情 |

不要求模拟新版 macOS 的玻璃材质。主内容采用实底以保证清晰；系统生物识别提示由系统提供，产品不能绘制一个冒充真实授权的窗口。

切换外观只影响显示，不重新渲染请求数据，不重置当前筛选、演示状态或确认窗口输入。生产 Flutter 主界面与 SwiftUI 确认窗口需遵循同一外观偏好；系统 Touch ID 窗口的样式仍由 macOS 管理。

## 4. 三类审核详情

共同字段：来源应用、用途、请求编号、密钥组、签名账户／公钥、环境、完整参与规则、已选参与集合、有效性。详情中的“核验信息”可展开查看输入摘要、策略／清单／份额版本、方法版本和原始内容；普通审核过程不要求理解这些实现名词。

| 场景 | 默认展开的信息 | 必须说明的含义 |
| --- | --- | --- |
| 业务 Ed25519 | 业务域、受众／执行系统、操作 ID、操作类型、资源、实际审批数据与变更前后值（如适用）、签发／到期时间 | “签署业务审批数据”；不能用付款成功图标暗示资金已转移 |
| Hyperliquid | Testnet／Mainnet、交易账户、签名账户、vault（如有）、资产、买卖方向、数量、限价／订单类型、reduce-only 和其他订单条件、最晚提交时间 | 最晚提交时间不等于订单自动撤销时间；nonce 可在核验详情查看；下单与 API wallet 授权为不同操作 |
| Solana 交易 | 集群、交易版本、费用付款人、本组签名账户、收款方、资产／数量、全部指令和程序、账户权限变化、预估费用的来源、有效高度、外部签名状态 | 本组聚合公钥占一个签名槽；MPC 参与人不占多个链上签名槽；费用估算不等于最终执行保证 |
| Solana 链下消息 | 独立用途组、消息域、完整原文、受众与有效性条件 | 方法和消息标准未开放时明确“不支持”，不能由交易签名入口代签任意字节 |

未知指令、来源权限不符、解析内容与待签输入不一致时，审核页保留可解释的诊断并禁用签名；不提供忽略风险的盲签按钮。示例原型只演示少量已解释操作，不代表完整指令白名单。

## 5. 审核、原生确认与结果追踪

### 5.1 正常路径

1. 打开请求，核对实际操作与来源。表达同意仅记录参与意愿；当前不满足规则时显示缺少的具体角色。
2. 合法在线集合就绪后冻结本次参与人和内容。界面显示“本次参与：指定 Agent + 当前审核人”等具体名单。
3. 打开 SwiftUI 原生确认窗口，再次显示同一份不可变内容。用户确认后，实际访问受保护 Keychain 材料触发系统 Touch ID。
4. 所选参与端执行协议；显示“共同签名中”，结束后先展示“签名已完成并验签”。不会为了等待其他人而长期保持份额解锁。
5. 按请求约定交付或提交：仅签名请求停在“签名完成，未请求提交”；Solana 外部签名未齐时停在“本组签名完成，等待其他签名”。业务签名交付后显示“已交付／待业务系统回执”；满足提交条件的链交易显示“已提交／待确认”。只有取得对应结果证据才更新完成状态。

原型中的“模拟 Touch ID 通过”和“演示状态”只用于设计评审，始终带模拟说明；生产 UI 不包含这些按钮。原型可以演示状态变化，但不能拿它证明真实授权或密码协议正确。

### 5.2 原生确认窗口

窗口标题使用动作，如“确认本次共同签名”。内容依次是：用途和环境 → 实际操作 → 密钥组规则 → 本次名单 → 有效性；展开项提供完整核验信息。内容不可编辑，若要变更业务字段，应回上游修改并生成新请求。

“批准并签名”请求本次授权；“返回核对”只关闭确认，不自动记为拒绝。Touch ID 取消／失败不会显示已签名；失败原因就近说明，可在仍有效的前置条件下重新准备，不能复用上一次解锁。

系统认证文案要明确使用的是当前设备支持的认证方式，不在不具备 Touch ID 的设备上显示可用的指纹入口；不要添加“永久信任此 Agent”或“以后免验证”开关。参考 [Apple：Managing accounts](https://developer.apple.com/design/human-interface-guidelines/managing-accounts) 中的认证命名与能力检查原则。严格指纹、是否允许密码回退仍是待确认的产品策略。

### 5.3 状态与操作矩阵

| 状态 | 用户文案 | 可以做什么 | 不可做什么 |
| --- | --- | --- | --- |
| 待核对 | 待你审核 | 看内容、同意参与、明确拒绝 | 把同意计为已签名 |
| 等待合法集合 | 还需 1 名人工／指定 Agent 未就绪 | 查看具体缺失成员、撤回本次参与意愿 | 解锁后无限等待、换人绕过规则 |
| 同组被占用 | 此密钥组正在处理另一请求 | 查看排队原因、查看正在运行的任务 | 同组并发签名或维护 |
| 待本次授权 | 参与人已就绪，待你确认 | 打开原生确认、返回核对 | 延用旧内容或旧名单的授权 |
| 协议执行中 | 正在共同签名 | 查看进度、请求停止 | 承诺停止等于撤销签名 |
| 已签名 | 签名已完成并验签 | 查看签名证据和交付状态 | 显示交易已确认 |
| 仅签名请求 | 签名完成，未请求提交 | 交付约定的签名结果 | 未获提交授权就广播 |
| Solana 签名未齐 | 本组签名完成，等待其他签名 | 返回部分签名结果、查看缺少的签名槽 | 把 MPC 门限满足当成全部链上签名齐全并提交 |
| 已提交 | 已提交，等待确认 | 按原操作标识查询 | 因等待过久自动生成第二笔请求 |
| 签名结果未知 | 结果待核对，可能已产生有效签名 | 查询／恢复原结果、查看证据 | 自动重签、新 nonce／blockhash |
| 提交结果未知 | 签名已完成，提交结果待核对 | 保留原签名证据，按原交易标识查询 | 把未收到回执当成未执行、自动发第二笔操作 |
| 取消后发现签名 | 已请求取消，但仍发现有效签名 | 查看证据和后续核对结果 | 自动交付或自动提交、宣称签名失效 |
| 已过期／版本变化 | 已停止新尝试；已有结果继续核对 | 查看原因，等待上游生成新请求 | 用过期状态覆盖已签或未知结果 |
| 本地授权不可用 | 本机暂时无法参与签名 | 查看设备能力、保护项状态与恢复说明 | 静默换密码或上传秘密给服务器 |
| 无法解析／验签失败 | 无法确认实际内容／结果校验失败 | 查看错误码与原因、退回接入方 | 忽略后继续签名或交付 |

“明确拒绝结束当前请求”是原型采用的建议默认值；若未来产品允许其他人继续达成门限，必须先独立设计策略和文案。键盘 Esc 关闭窗口不是明确拒绝。

## 6. 建组与维护

### 6.1 首次配对与建组

配对流程依次显示邀请范围和有效期、工作空间／成员身份核对、本机能力检查、可信渠道核对提示。邀请不是签名份额，也不因为点击邀请就产生密钥。

创建密钥组的配置包括用途、允许的网络／接入应用、成员和规则。纯人工至少 2 人；指定 Agent 模式分别设置 Agent 与人工 k-of-m。Hyperliquid 用途锁定人机模式；其他用途不因相同算法而共用一组密钥。

提交配置后仅创建提案。进度为“全员核对提案 → 全员在线建钥 → 各端持久化 → 全员激活确认 → 可用”。成员的指纹与本地份额不在页面中混为一谈；公开公钥只有建钥完成后出现。原型可简化到提案确认状态，不宣称已实现 DKG。

### 6.2 维护与恢复

| 操作 | 入口说明与确认内容 | 不满足条件时 |
| --- | --- | --- |
| 固定成员份额刷新 | 公钥、成员和规则保持不变；需要全员在线；暂停新签名；显示每方准备和切换确认进度 | 显示具体离线成员。准备之后遇故障保持冻结，不能出现“超时退回旧份额”按钮 |
| 成员／门限／角色变更 | 入口名为“新建组并迁移”；明确生成新公钥，随后迁移上游信任／资产授权 | 新组完成不显示旧资产迁移成功；旧组不足授权时说明限制 |
| 本人备份与恢复 | 仅处理本人加密备份；显示当前组、公钥、成员与版本核验。密文和恢复密钥分开保管 | 不提供集中导出全组份额、复制秘密或管理员代解锁 |
| 更换设备 | 验证备份与当前版本，按现有规则授权新绑定，各应确认设备同步后激活 | 无合法维护组合时保持冻结；备份存在不等于一定可恢复 |

备份保管方式和恢复授权仍需产品与部署方确认；原型入口只说明条件和状态。不能承诺支持任意旧备份恢复。

原型对同组签名中或签名结果待核对的情况保守禁用刷新，先处理原尝试；其他密钥组不受影响。生产中的维护准入必须依据核心的本地运行状态和结果证据，不能只依赖页面按钮禁用。

## 7. 空、加载、离线与可访问性

| 情景 | 设计处理 |
| --- | --- |
| 暂无待办 | 显示“暂时没有需要你处理的请求”；保留筛选和历史入口，不推荐创建无关交易 |
| 搜索无结果 | 显示当前搜索条件与清除入口，不让空列表看起来像同步故障 |
| 正在加载／同步 | 保留当前位置和已知状态，显示更新时间；确认内容未完成校验时不可签名 |
| 与协调服务断开 | 明确连接丢失；禁止启动新尝试；运行中的尝试按其实际结果处理，不能统称失败 |
| 重复点击 | 关键操作处理中禁用再次触发，避免多个确认窗口或重复尝试 |
| 长地址／长业务内容 | 提供完整查看与合理换行；省略号只用于列表，最终核对必须可见完整内容 |

所有操作可用键盘到达，焦点样式清楚；模态窗口有标题、焦点范围和关闭后的焦点恢复。状态不只依赖颜色，屏幕阅读器能读到角色、状态和错误；动态进度适度播报，尊重减少动态效果的系统偏好。原型验证范围以 [原型检查记录](VERIFICATION.md) 为准，不能据此宣称通过真实 VoiceOver 或原生无障碍验收。

## 8. 设计交付与实现边界

- 本目录的 HTML/CSS/JS 是无真实凭据的评审原型；不作为签名软件发布或安全边界实现。
- 生产主界面由 Flutter 承担；原生确认与系统授权由 SwiftUI／Swift 承担；两者展示同一共享核心生成的验证模型。
- 演示数据和状态控件不进入生产。生产中的状态转换以已验证的核心事件和服务证据驱动，不能以动画结束判断成功。
- 本次先评审 PRD、页面与状态，不承诺完整移动端、主网上线或其他链兼容。待定项集中在 [PRD §6.4](../PRD-keymux.md#64-技术方向与待定项)。
